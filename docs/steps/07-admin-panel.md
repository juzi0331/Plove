## 一、范围：先定死做哪些，比做多少更重要

后台能塞的东西是无限的（上传爬虫、源开关、公告、日志、指标图……）。
所以先划了两个圈，**只做圈里的**：

| 圈 | 内容 | 为什么先做它 |
| --- | --- | --- |
| **A · 只读看板** | 缓存命中、预热状态、每个源的健康（含"探过没有"） | 排查"为什么这个源没内容了"时必需，而且**零风险**（不会误伤用户） |
| **B · 码与设备动词** | 发码 / 停用 / 解封 / 延长 / 看设备 / 踢设备 | 这是**最常做的日常动作**，而且现在不做就只能进数据库 |

**明确不在这一步**（都写了理由，不是漏了）：

* **上传爬虫 / 改源开关** —— 前者是**远程代码执行入口**，形态得先想清楚
  （谁写、怎么审、坏了怎么回滚）；后者要先有"远程配置"那张表（阶段 6b-3）。
* **看用户行为、看播放统计** —— 我们没有埋点，也没有必要为用户 < 30 人的场景做这个。

## 二、四个决定了整个后台形状的选择

### 1. 挂在**同一个域名的 `/admin` 下**，不另开端口、不做独立站

用户端是 `/`，后台是 `/admin`，同一份 nginx、同一张证书、同一个后端进程。

**为什么不做成独立站点：** 后台要做的事（缓存状态、预热、源健康）**全都在后端进程的内存里** ——
独立部署就要再引入一套"后台怎么问后端"的接口，等于把已经有的东西再包一层。
同源还顺带免掉了 CORS 和第二张 HTTPS 证书。

代价是必须处理一件事：**根组件 `App.vue` 对用户端和后台都生效**（见下面第 8 条坑）。

### 2. 后台令牌存 `sessionStorage`，不是 `localStorage`

用户端的设备令牌存 `localStorage`（关掉再开还要在），后台令牌**刻意不这样**：

| | 用户端设备令牌 | 后台令牌 |
| --- | --- | --- |
| 存哪 | `localStorage` | **`sessionStorage`** |
| 关掉浏览器再开 | 还在（不用重新输码） | **没了，要重新登录** |
| 为什么 | 用户不该每天被赶回激活页 | 这是**"能管这台机器"**的凭证。运维在别人电脑上登一下后台，关掉标签页就该失效 |

`PLOVE_ADMIN_TOKEN` 留空 = 后台全部 `403`（连登录页都进不去）—— 默认安全，
而不是默认敞开。

### 3. 响应里**永远不含设备令牌的明文**

设备列表只给 `token_prefix`（**前 6 位**），够运维说清"是这一台"，不够拿去冒充。

**为什么值得当硬规矩：** 后台页面会被投影、会截图、会不小心开着。令牌一旦出现在
响应里，就等于**每打开一次后台就泄露全部在线设备的凭证**。
`test_admin_codes.py` 里有一条贯穿全文件的断言：设备令牌的明文不能出现在任何后台响应里。

### 4. "踢" ≠ "封"（这是最容易做错的一条）

| | 踢设备 | 停用码 |
| --- | --- | --- |
| 改了哪个字段 | `active_device_id = None` | `disabled_at = 现在` |
| 那台设备 | 立刻停播 + 提示"已被别的设备使用"，**但还能自己抢回来** | 彻底进不来 |
| 设备记录 | **不删**（删了它就认不出自己了） | 保留 |
| 什么时候用 | "这台机器换人了 / 有点可疑，先请它下线" | "这个码作废了" |

**为什么踢不能自动重抢回来：** 如果客户端发现自己被踢就自动抢，两台设备会**无限互踢**，
用户看到的是画面疯狂中断。所以这条链是：**心跳回 `is_active:false` → 停播 + 提示 →
用户自己点"在此设备继续" → 抢回**。那个按钮是设计的一部分，不是装饰。

> 已知的、v1 不处理的边界：**管理员主动踢**和**另一台设备顶掉你**，
> 在客户端看到的是**同一样东西**（都是 `is_active:false`）。要区分得加一个"为什么"字段。

## 三、接口与契约

新增 **7 个**接口（后台接口总数 2 → 9，后端接口总数 12 → **19**）：

| 方法 | 路径 | 干什么 |
| --- | --- | --- |
| GET | `/api/v1/admin/codes` | 列表：搜码 / 搜备注（大小写不敏感）、分页、带真实用量 |
| POST | `/api/v1/admin/codes` | 发码（`days` 或 `hours` **二选一**，可一次发多张 + 备注） |
| POST | `/api/v1/admin/codes/{id}/disable` | 停用 |
| POST | `/api/v1/admin/codes/{id}/enable` | 解封 |
| POST | `/api/v1/admin/codes/{id}/extend` | 延长（见下） |
| GET | `/api/v1/admin/codes/{id}/devices` | 这个码用过的设备（含活跃位是谁） |
| POST | `/api/v1/admin/devices/{id}/kick` | 踢下线 |

新增 **9 个契约**（18 → 27）：`admin-code-item` · `admin-code-list` ·
`admin-issue-request` · `admin-issue-result` · `admin-extend-request` ·
`admin-code-action` · `admin-device-item` · `admin-device-list` · `admin-kick-result`。
另外给 `SiteHealth` 加了一个 **`probed`** 字段（见第七节第 4 条）。

### 列表要能回答"这个码被谁在用"

只把表 dump 出来是不够的，运维真正想知道的是**用量**。所以每个码额外算三个值：

* `remaining_seconds` —— 剩余时长（**0 有两种含义**：还没激活，或已过期；靠 `activated_at` 区分）
* `device_count` —— 有几台设备用过
* `active_device_name` —— 此刻**正在线**的那台（`null` = 现在没人在线）

搜索同时匹配**码**和**备注**，因为运维记得住的往往是备注（"给老王的"），不是那串字符。

### 延长为什么有**两种**分支

这是这一步唯一一个"必须先想清楚"的逻辑：

```
已激活的码   → 改 expires_at      （在现有到期时间上往后加）
未激活的码   → 改 duration_hours  （还没开始计时，加时长即可）
```

**为什么不能统一改一个：** 时长是**从首次激活起算**的（拍板决策）。
一个还没激活的码根本没有 `expires_at`，给它算到期时间等于凭空造一个起点 ——
用户激活时会被这个假起点直接影响（可能一激活就过期）。所以未激活的码只能加**时长**。

## 四、现在能干什么

| 页面 | 路由 | 能做的事 |
| --- | --- | --- |
| 登录 | `/admin/login` | 输后台令牌（存 `sessionStorage`） |
| 看板 | `/admin` | 缓存命中 / 预热状态 / 每个源的健康（5 秒自动刷新 + 手动刷缓存） |
| 码列表 | `/admin/codes` | 搜、发码、停用（**二次确认**）、解封、延长、**刷新** |
| 设备 | `/admin/codes/:id/devices` | 看设备（令牌只给前 6 位）、看谁在线、踢下线 |

技术上的两个小选择：

* **Element Plus 按需引入**（**不** `app.use(ElementPlus)`）—— 构建产物里已确认
  它被切进**后台自己的 chunk**，用户端首屏没有被它压重。
* **复用用户端的 `http.ts`**：同一套拆信封 / 超时 / 错误码翻译，只是多带一个
  `X-Admin-Token` 头。**没有为后台再写一遍请求层。**

## 七、联调时抓到并修掉的十个问题

前 8 个是这一步自己的，第 9 个是**被这一步逼出来的后端 bug**（最值得看的一条），
第 10 个是这一步的**副作用**：一旦真的去用后台，就会有三个测试变红。

### 1. `<video>` 还在 `v-if` 后面，赋值后立刻挂会**静默失败**

给 `playback` 赋值之后立刻去拿 `videoEl` —— 那一刻 Vue 还没把它渲染出来，
`attachPlayer` 拿到的 `null`，然后直接 `return`。**不报错、不警告、请求全 200**。
改成 `await nextTick()` 之后再挂，并且拿不到元素时 `console.warn`。

> 这类失败只看请求日志会得出"一切正常"的结论 —— 和步骤 6 里那条是同一类。

### 2. "防盗链"提示误报

一开始写成"`playback.headers` 非空就提示这个源需要代理"，而 `ncat21`
明明能播也弹。改成**只在真的播不出来时**才显示。
**一个总出现的警告等于没有警告。**

### 3. 生成器误报 6 处"契约冲突"

`VodItem` 这类类型在多份契约里各定义了一份（独立的 `vod-item.json`，以及嵌在
`catalog-home.json` 等 `$defs` 里的副本），独立那份带 `description`、副本没有 ——
语义相同、JSON 文本不同。改成**比较生成的 TS 文本**，而不是比 JSON。
我们真正关心的是"会不会产生不同的类型"，注释差异不影响这一点。

### 4. 看板的 `guards()` 只列**碰过**的源，于是打开是空表

这是"比没有更糟"的一种情况：一个空表看起来像"没有源"，而不是"还没探测"。

改法：`registry.guards()` **按目录扫描**（`sites/` 下有哪些源就列哪些），
并给 `SiteHealth` 加一个 **`probed`** 字段区分"没探测过"和"探测结果是健康/熔断"。

> 契约级回归：`test_status_lists_sites_before_they_are_ever_used`（打开就是全表）和
> `test_probed_flips_after_a_real_request`（真打一次请求后它要变 true）。

### 5. 写操作**显式提交**：`get_db` 的自动提交发生在响应之后

运维点完"停用"，那一行**偶尔还是旧值**（虽然 40 次探针 0 复现，窗口在毫秒以下）。
原因是 `get_db` 的 `commit()` 跑在**依赖清理阶段**（响应送出之后）。
改法：写接口一律显式 `commit_now(db)` —— **客户端读到 200 时，变更已经落库。**

当时认为窗口小到可忽略；**这一条在第 9 条上被打脸了。**

### 6. 后台码列表**没有刷新按钮**

5 秒自动刷新只做在看板上，码列表没有 —— 于是运维点完停用、想确认状态，只能自己 F5。

### 7. `App.vue` 是用户端 / 后台**共用**的根组件

用户端那个"已在别的设备上使用"的弹窗**漏进了后台**：浏览器里那份设备令牌刚好被
别人顶掉，运维在后台就看到一个莫名其妙的、带着用户语义按钮
（"在此设备继续"会去**抢活跃位**）的弹窗。已加 `isAdminRoute` 判断。

> 教训：**"全局"的横切关注点要先问一句"它对不对后台生效"。**

### 8. 被踢后抢回活跃位，**过期的错误还挂在屏幕上**

被踢那一刻，当前页面上的请求拿到 `SESSION_KICKED`，于是**当场变成一个错误态**
（首页 / 分类 / 详情 / 播放都不例外）。用户点"在此设备继续"，会话是好了，
**但那个错误还挂在屏幕上** —— 他得自己发现"重试"按钮。

改法：设备 store 新增一个 `restoredAt` 信号（每成功抢回一次变一次），
四个视图 `watch` 它然后自动重载。用户感觉就是"点了一下，画面回来了"。

### 9. ★ 抢回活跃位之后的**第一个请求**，可能仍然被判定为"被踢"

第 8 条修完，在浏览器里复测，**只过了一半**：服务端的网络日志是这个顺序 ——

```
POST /admin/devices/7/kick                     → 200   （后台踢）
GET  /sites/ncat21/category?tid=2&page=1       → 409   （用户端被踢，错误态 + 弹窗）
POST /activation/redeem                        → 200   （点"在此设备继续"，成功）
GET  /sites/ncat21/category?tid=2&page=1       → 409   ← 又 409！界面再弹一次"已在别的设备上使用"
```

**先排除前台**：用 curl 手工走同样的顺序（踢 → 409 → redeem 200 → 请求）**每次都是 200**。
差别只有一个：curl 两次请求之间隔了十几毫秒（进程启动），而浏览器**只隔一个响应往返**。

**根因**：`activation/redeem` 只 `flush()`，提交交给 `get_db` ——
而 `get_db` 的 `commit()` 跑在**响应送出之后**（第 5 条那个坑，同一个根因）。
于是客户端拿到 200 立刻发的下一个请求，读到的还是 `active_device_id = NULL`。

**为什么这个必现而"停用"那个几乎不现**：这里的时序是**必然的** ——
客户端抢回活跃位之后一定会立刻重新拉数据（第 8 条那个自动重载），中间只隔一次往返。
而在 MySQL 上每次提交都要 fsync，窗口有几毫秒，撞上的概率**大约是一半**。

**改法**：把第 5 条那个 `_commit` 提升成 `app.api.deps.commit_now()`，
`/activation/redeem` 也显式调它 —— 一处规则，两个调用方。

**怎么测**：这种"毫秒级时间差、一半概率复现"的 bug，靠手点等于掷骰子。
所以测试**把时间差放大成必然**：把 `get_db` 换成一个**不提交**的版本
（模拟"响应已送出、事务还没落库"），然后断言"抢回之后的第一个请求必须放行"。
新文件 [backend/tests/test_activation_commit.py](../../backend/tests/test_activation_commit.py)。
实测：**把 `commit_now` 去掉，这个用例立刻红**；加上就绿。

> **这条值得记住的教训：** "窗口很小，可以忽略"和"时序上是必然的"是两件事。
> 后者只要概率不是 0，在真实使用频率下就一定会发生。

### 10. 后端测试隐式依赖开发机的 `.env`

把 `PLOVE_ADMIN_TOKEN=admin` 写进 `backend/.env`（**这一步的必然结果** ——
不配就用不了后台）之后，跑测试变成 **3 failed**：

```
test_admin_is_off_until_a_token_is_configured      assert 401 == 403
test_write_endpoints_are_guarded                   assert 401 == 403
test_write_endpoints_refuse_when_no_token_configured  assert 401 == 403
```

原因：`fake_settings` 是直接 `Settings(...)` 构造的，而 `Settings` 会去读 `.env` ——
于是"没配令牌"的夹具里其实**有**令牌，而那三个用例测的正是那条
**"空令牌 = 后台整体 403"** 的安全默认值。

**为什么这条值得单独记：** 这三个用例本来是用来**防止后台裸奔**的，
结果它们自己是最脆的一个 —— 随着开发机的配置变化而变红，而变红的原因
和它们想守的东西完全无关。人一旦习惯"这仨红是正常的"，这条防线就没了。

改法：夹具里**显式钉成空**（`admin_token=""`），需要令牌的用例自己 `_enable_admin`。
立一条规矩：**测试不能依赖开发机上的 `.env`。**

| **前端精细化（7b）** | 骨架屏 / 排版 / 错误文案，对着真数据调 |
| 后台补完 | 上传爬虫（要先定安全模型）、审计日志查询界面、分页跳转 |

> 顺序上仍然建议：**先做远程配置再深挖前端**。它是"加法"（新增一个 `config` 接口
> 和几个字段），不会改变现有 19 个接口的形状，现在改成本最低。
> **但一旦远程配置要改现有接口的语义**（比如 kill switch 要让内容接口回一个特殊错误码），
> 那条"先后端后前端"的理由就又生效了。

> 另外有一件事**建议早做但没排进计划**：把 `PLOVE_ADMIN_TOKEN` 从环境变量换成
> 一个能改的凭证（现在改它要重启进程）。只要有第二个人要用后台，这件事就会立刻变得紧迫。

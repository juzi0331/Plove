## 一、`--play-id`：播放快 45%

### 原来慢在哪

`ncat21` 的 `play --id X --ep N` 内部会**先调一次自己的 `detail()`**，
只为把"线路 N 第 M 集"翻译成播放页的路径。而详情页实测要 **3.5~5.9 秒**。

可是**上层本来就有那个路径** —— `detail` 返回的每一集都带着 `play_id`。

### 改法

给命令行协议加一个**可选**参数 `--play-id`：

```
python sites/ncat21.py play --id 369061 --ep 1 --line 1     # 老路径：内部会抓一次详情
python sites/ncat21.py play --play-id /play/369061-41-4969745.html   # 新路径：直接去播放页
```

后端把 `playback` 接口的 `play_id` 查询参数原样透传下去。**不传也能用** ——
它是"加速"，不是"新要求"，所以老客户端不会因此坏掉。

### 实测

```
play 老路径（内部先抓详情）   7.249s
play 带 play_id（只抓播放页）  3.981s      ← 省 3.3 秒（45%）
```

### 代价：这是一处新的信任边界

`play_id` 由**客户端回传**，而爬虫会拿它**直接去 `fetch`**。
一个绝对 URL 就能让我们变成任意地址的抓取代理（SSRF），
而且抓回来的东西还会当成播放地址吐给用户。三层都拦：

| 层 | 做法 |
| --- | --- |
| 后端（[catalog_service](../../backend/app/services/catalog_service.py)） | 不像站内定位符就**丢掉并回退**，不报错 —— 它是加速用的，不该成为一个新的失败原因 |
| 爬虫（`clean.safe_relative_path`） | 再拦一次：必须站内相对路径、拒 `//evil.example/x`、拒反斜杠、拒 `..` 段 |
| 测试 | 两边各有一组"绝对 URL / 协议相对 / 反斜杠"的用例，断言**没有真的发出去** |

**`//evil.example/x` 值得单独说：** 它是"协议相对 URL"，拼上 base 之后
主机就被换掉了。只检查"以 `/` 开头"的实现会**正好把它放过去**。

## 二、全局限额：两层保护的是两件事

```
每站上限 2  ──► 保护源站的耐心（别一个人点两下就打两轮）
全站上限 4  ──► 保护这台 VPS（10Mbps、单核都不富裕）
```

没有全站上限的话，源变多之后总量是**乘出来**的：
10 个源 × 2 = 20 个并发子进程，内存和 CPU 一起完蛋。

三个实现细节：

* **全局限额属于注册表**（也就是整个进程），不属于某一个源 ——
  它在 `SiteRegistry` 里造一份、分给每个守护，`guards()` 快照里也会带出来。
* **固定的获取顺序：先每站、再全局。** 顺序固定就不可能形成环，也就不会死锁。
  反过来写就会：一个人持着全局等某个站，另一个人持着那个站等全局。
* **两层共用一个等待预算**（而不是各等一次 `queue_timeout`）。
  各等一次的话最坏要干等两个周期，前面那些请求早超时了。

两种"忙"要分得清：

| 错误消息 | 含义 |
| --- | --- |
| `ncat21 正忙（并发上限 2），排队 20s 仍没有空位` | 这个源被占满了 |
| `全站并发已满（请稍后重试，或调大 …）` | 整个后端被占满了 |

## 三、主动预热：解决 TTL 的固有毛病

### 病在哪

TTL 是**被动过期**，这带来三个现象：

```
第 0 分钟   有人访问 → 抓一次（1~9 秒），存起来
第 1~9 分钟 所有人秒开
第 10 分钟  有人访问 → 发现过期 → **他要等 1~9 秒**重新抓   ← 由一个倒霉的用户承担
```

再加上：**没人来就永远不会抓**（数据一直旧着），
以及**重启后缓存全空**（第一批用户一起等，冷启动）。

### 治法

定时（默认 24 小时）主动把每个源的**入口页**抓一遍填进缓存。

```
                       ┌─ 冷启动：启动 60 秒后先跑一轮（别和启动时的第一批请求抢源站）
定时任务 ──► 预热一轮 ──┼─ 每个源：首页 + 前 3 个分类的第一页
                       └─ 结果写进缓存，并把耗时/成败记下来给后台看
```

**只热入口，不热全部：**

| 对象 | 热不热 | 为什么 |
| --- | --- | --- |
| 首页 | ✅ | 入口，一个站一次请求，性价比最高 |
| 前 3 个分类的第一页 | ✅（可配） | 用户点进分类最先看的就是它 |
| 详情 | ❌ | 有无穷多部片，全热 = 定时自己去爬整个站，那是主动给源站压力 |
| 播放地址 | ❌ | 带时效签名，热了也是废的 |

### 两条必须守住的性质

**一、预热走的是和在线请求完全相同的那条路。** 它调的是
`catalog_service` → `registry.run` → 每站守护，所以并发上限、熔断、
契约校验一个都不会绕过。**挂掉的源在熔断期内根本不会被预热撞到** ——
它会在 `UPSTREAM_CIRCUIT_OPEN` 上瞬间返回，而不会每 24 小时准点去捅它一次。
（有测试专门盯这条。）

**二、`force` 是必须的。** 预热要**换掉**旧值，不能只读一遍缓存。
没有 `force` 的话，如果 TTL（比如 25 小时）比周期（24 小时）长，
预热就变成"每天读一遍缓存"，什么也没做 —— 而那正是推荐的配置组合。

### 默认关

`PLOVE_WARMUP_ENABLED` 默认 **false**：它会在**没人访问的时候也去请求源站**，
属于"默认打开会很意外"的一件事。生产显式打开（见 `.env.example`）。

推荐组合：**周期 24 小时 + TTL 25 小时**。这样缓存永远不会因为自然过期
而被普通请求重新触发。

### 实测

```
预热一轮耗时 31.4s，2 个源
  ai2048   ok=True  首页22条 分类3个  8.5s
  ncat21   ok=True  首页75条 分类3个 22.9s
```

看这个数字就知道**为什么它不能是同步接口**，以及**为什么详情不该预热**：
2 个源、各 4 个页面就 31 秒；20 部详情的量级就是几分钟。

## 四、后台接口：能自己看，也能手动刷

```
GET  /api/v1/admin/status            缓存 + 每个源的健康 + 上次预热的结果
POST /api/v1/admin/cache/refresh     手动跑一轮；?wait=true 会等它跑完
```

鉴权用 `X-Admin-Token`（`.env` 里的 `PLOVE_ADMIN_TOKEN`），和激活码**两套凭证**：
激活码管"谁能看内容"，它管"谁能管这台机器"。

两条刻意的处理：

* **没配令牌就一律拒绝**（403）。空令牌必须永远不能通过 ——
  否则一个忘了配变量的部署就等于把后台裸奔在公网上。
* **用 `compare_digest` 比较**。普通 `==` 会在第一个不同的字符处提前返回，
  从响应时间上能一个字符一个字符地把令牌猜出来。

**为什么 `refresh` 默认不等：** 一轮 31 秒，卡在一个 HTTP 请求里先超时的是反向代理，
而你会以为"按钮坏了"。默认立刻返回 + 用 `/admin/status` 看进度，是更诚实的做法。
（`?wait=true` 留给 curl 和运维手动操作。）

### 顺手修了一个隐蔽的 bug：两套凭证撞名

加完后台那套 `X-Admin-Token` 后才发现：`APIKeyHeader` **不给 `scheme_name` 时
用类名当 scheme 名**，两个都是 `"APIKeyHeader"`，于是后声明的那个
**直接覆盖**了前一个。后果很具体：

```
OpenAPI 里只剩一个 scheme，而且名字写的是 X-Admin-Token
→ Swagger 里点 /api/v1/sites 会发 X-Admin-Token
→ 每个内容请求都 401，而你会以为是自己激活码错了
```

修法是各自给一个 `scheme_name`（`DeviceToken` / `AdminToken`）。
顺手加了一条**契约级回归测试**（`test_openapi_declares_both_credentials`）：
它直接断言 OpenAPI 里有**两个** scheme、各自指向正确的头，
并且**每个接口引用的是哪一个**也对 —— 这种东西不能靠人记得。

### 为什么"看状态"值得单独做一个接口

排查"为什么这个源没内容了"时要同时看到四件事，缺任何一件都只能靠猜：

1. 缓存有没有货（`cache.size` / `hits`）；
2. 熔断是不是开着（`sites[].state` = `open`？还有多久冷却完 `retry_after`）；
3. 上次预热什么时候跑的、哪个源失败了、错在哪个错误码；
4. 缓存 TTL 现在是多长（可能有人把它设成了 0）。

## 七、顺手揪出的问题：超时配小了

验证 `play_id` 时，`ncat21` 的详情**真的超时了一次**（10 秒上限）。回头一量：

| 命令 | ai2048 | ncat21（本次实测） | ncat21（上次实测） |
| --- | --- | --- | --- |
| home | 2.0s | **8.9s** | 5.2s |
| detail | 1.0s | **5.9s** | 3.5s |
| play（不带 `play_id`） | 1.0s | **7.2s** | 4.1s |
| play（带 `play_id`） | — | **4.0s** | — |

之前是按"ncat21 约 4s"配的 10 秒，结果源站慢下来就顶不住了。
改成 **20 秒 / 25 秒**（约 2 倍余量）。

**代价是诚实的：** 极端情况下一个请求会多占一会儿线程。
但线程数本来就受并发上限约束（最多 `global_max_concurrency` 个），
所以最坏情况也是可控的 —— 而"平时刚好、网络一抖就 504"会让用户
以为这个站彻底坏了，那更糟。

`ncat21` 慢是它自己造成的：它带 1 秒主动限速，一个页面要 2~3 次请求。

**后续更好的做法**（记在 [PROGRESS.md](../../PROGRESS.md)）：把超时做成
**按源可配**，写进源的 `meta`。源自己最清楚自己的节奏。

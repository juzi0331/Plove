## 一、这一步干了什么

给后端装上**"源站出问题时不会拖垮本站"**的能力。一句话概括交付物：

| 交付物 | 位置 | 解决什么 |
| --- | --- | --- |
| 内存缓存（TTL + LRU） | [app/cache/ttl.py](../../backend/app/cache/ttl.py) | 同一份数据不要抓第二遍 |
| 请求合并（防击穿） | [app/cache/singleflight.py](../../backend/app/cache/singleflight.py) | 缓存**刚好过期那一瞬间**的并发，只放一个进去 |
| 内容缓存策略 | [app/cache/content.py](../../backend/app/cache/content.py) | 缓存谁、缓存多久、失败怎么办 |
| 站点守护（并发上限 + 熔断） | [app/crawler/guard.py](../../backend/app/crawler/guard.py) | 源站坏了之后，别再每个请求都去陪它耗满超时 |

## 二、为什么"缓存"和"防击穿"是两件不同的事

这是这一步最容易被误解的地方。**缓存挡不住击穿**：

```
时间轴 →
请求 A ──┐
请求 B ──┤ 缓存刚好在这一刻过期
请求 C ──┤
请求 D ──┘
         ↓
  4 个请求同时发现"没缓存" → 各自去抓一次 → 4 个子进程、4 次源站请求
```

缓存的作用是"**先后到达**的重复请求只抓一次"，而**同时到达**的那批它一个也挡不住。
偏偏"刚好过期"这一刻正是并发最集中的时候（首页被反复刷新时尤其明显）。

所以是两个组件配合：缓存负责平时，`SingleFlight` 负责那个瞬间 ——
同一个 key 只放一个"领跑者"进去，其余人**等同一份结果**（失败也一起失败，
否则第一个人的失败会变成其他人的"未命中"，于是他们各自重试，源站承受的
正是我们想避免的重复流量）。

## 三、缓存谁、缓存多久

按"这东西多久会变"来定，不是按"能省多少"来定：

| 命名空间 | 默认 TTL | 为什么 |
| --- | --- | --- |
| `home` | 10 分钟 | 分类树与首页推荐几乎不变，却要 fork 一次子进程 |
| `category` | 5 分钟 | 列表随新片上架变化，但不需要秒级 |
| `detail` | 5 分钟 | 剧集列表会更新；用户来回点同一部片很常见 |
| **`playback`** | **不缓存** | **地址带时效签名**（`auth_key` / `timestamp`），缓存等于把失效地址发给用户 |
| `search` | 不缓存 | 关键词近乎无穷，命中率低 |

**TTL 设成 0 就等于关掉这一类缓存** —— 运维要能一键关掉，不用改代码。

### 只缓存成功的结果

把一次网络抖动缓存 5 分钟，用户会以为整个源站坏了，而重试一次很可能就好。
所以错误一律**穿过**缓存。有测试盯着这条（`test_errors_are_not_cached`）。

### "拿旧值兜底"（stale-while-error）刻意**没做**

那个东西会把"源站已经挂了"伪装成"一切正常"，而这个项目一直在坚持
**错误要诚实**（比如"该源不支持搜索"不许伪装成"搜到 0 条"）。
真要兜底，应该由调用方显式决定，而不是在缓存层悄悄发生。

**唯一的例外**是 `meta`（见下）—— 它有明确的理由。

## 四、熔断：省下的其实是最贵的东西 —— 超时

一个挂掉的源，如果每个请求都要耗满 10 秒才失败，50 个请求就是 **500 秒的线程被占着**。
熔断之后它们在**微秒级**返回。

```
连续失败 5 次（默认）──► 打开电路 ──► 冷却 60 秒内：立刻回 UPSTREAM_CIRCUIT_OPEN
                                        （一次源站请求都不发）
                                           │
                                           ▼ 冷却结束
                                      放**一个**探针试探（半开）
                                        ├─ 成功 → 恢复
                                        └─ 失败 → 重新开始下一轮冷却
```

半开只放**一个**探针：放开全部等于把刚缓过来的源站再打一遍（惊群）。

### 什么算"源站故障"，什么不算

这是最容易做错的一处。**不是"任何错误都算"**：

| 错误码 | 计入熔断？ | 为什么 |
| --- | --- | --- |
| `UPSTREAM_TIMEOUT` / `HTTP_ERROR` / `PARSE_ERROR` / `BLOCKED` / `UNKNOWN` | ✅ 计入 | 源站出问题了 |
| `NOT_FOUND`（这部片下架了） | ❌ **不算** | 这是**正确的回答**，不是故障 |
| `UNSUPPORTED`（该源没有搜索） | ❌ **不算** | 同上 |

把它们算进去，用户点几个失效链接就能把整个源"熔断"掉 —— 典型的误伤。

### 并发上限

一个源同时最多跑 2 个爬虫子进程（默认）。抢不到槽位就排队，
排 20 秒还没空位就明确回 `UPSTREAM_BUSY`。

**为什么宁可直接失败也不无限等：** 等待会连着占住连接和线程，
最后大家一起超时（雪崩的标准剧本）。快速失败至少让用户马上看到发生了什么。

## 五、踩到的一个真坑：`meta` 的成功会把内容失败清零

写完第一版测试就红了。原因是：

`run()` 每次都会**先跑一次 `meta`**（拿能力清单），而那时我的实现里
"任何成功都清零失败计数"。于是序列变成：

```
内容失败 → 计数 = 1
meta 成功（每请求必经）→ 计数清零
内容失败 → 计数 = 1
meta 成功 → 计数清零
...永远到不了阈值 → 永远熔断不了
```

而"**meta 能通、抓内容就超时**"恰恰是最需要熔断的那类源
（`ncat21` 的详情页就常常比它的 meta 慢得多）。第一版等于把熔断
做成了一件永远不生效的摆设。

修法：`meta` **只走并发限流，不参与熔断判定**（`counts_as_health=False`）。
理由是它本来就"不能作为健康证据"——它被缓存、还可能拿旧值顶替
（见下一节），所以它成功不代表现在抓得到内容。

这条现在有专门的回归测试：`test_healthy_meta_does_not_reset_content_failures`。

## 六、`meta` 的降级：见过的源不会凭空消失

`meta` 取不到时**拿上一次的值顶上**，而不是让这个源从站点列表里消失。

为什么值得特殊对待：源临时抽风时，如果 `/sites` 里少了一项，前端那个
"资源站下拉框"会**忽然少一个站**，用户的第一反应是"这个站被下架了"，
而不是"它现在有点问题"。而点进去自然就会看到真正的错误 ——
**那个错误是诚实的**。

从没成功过的源（爬虫文件一开始就是坏的）照旧被跳过，不会凭空出现。

## 八、接口有没有变

**一个都没变。** 缓存与守护完全在内部，前端拿到的东西一模一样：

| 变化 | 说明 |
| --- | --- |
| 新增两个错误码 | `UPSTREAM_BUSY`（该源并发满了）、`UPSTREAM_CIRCUIT_OPEN`（该源已熔断），都是 **503** |
| 契约更新到 16 个 | `error-info.json` 的枚举多了这两个码 —— 前端**必须**按 `code` 分支处理，不要按 HTTP 状态猜 |

把这两个码和 `UPSTREAM_BLOCKED` 分开是有意的：
"源站拦了我们"、"我们这边忙"、"我们自己把它熔断了"，
对排查问题是三件完全不同的事。

## 十、这一步**没有**做什么

| 没做 | 为什么 |
| --- | --- |
| Redis / 分布式缓存 | 用户小于 30 人、单实例，内存缓存命中率和它一样，却少了"多一个必须活着的组件" |
| 拿旧值兜底（除 meta 外） | 会把"源站挂了"伪装成"一切正常"，破坏错误的诚实性 |
| 全局并发上限 | 现在只有 2 个源，每站 2 个槽位够了。源变多时要加（否则 10 个源 × 2 = 20 个子进程） |
| 缓存预热 / 定时刷新 | 没有明确收益，且会在源站不稳时雪上加霜 |
| 把守护状态暴露成接口 | 属于后台面板（阶段 7）。现在 `registry.guards()` 已经能出快照，缺的只是接口 |
| 播放地址缓存 | 地址带时效签名，**永远不该做** |

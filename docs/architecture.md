## 一、先想清楚：这个系统真正的难点在哪

不是"页面好不好看"，也不是"能不能爬到"。真正的三个难点是：

| 难点 | 本质 | 谁最容易死在这上面 |
| --- | --- | --- |
| 源站多变 | 同一个功能，十个站十种结构（HTML / JSON API / 加密 JS / 防盗链） | 爬虫层 |
| 播放地址强时效 | m3u8 带 token，几分钟到几小时就失效 | 后端 |
| 采集会拖垮在线服务 | 一个站超时，全站用户一起转圈 | 后端 + 爬虫的边界设计 |

所以整套架构只需要回答三个问题：**爬虫怎么和在线服务解耦**、**播放地址怎么随点随取**、**数据契约归谁定义**。

## 二、三层 + 一条契约总线

```
                         ┌──────────────────────────┐
                         │   contracts/ (唯一事实源) │  JSON Schema
                         └────────────┬─────────────┘
                           生成类型    │    校验入参/出参
        ┌───────────────────────────────┼───────────────────────────────┐
        │                               │                               │
   ┌────▼─────┐   HTTP/JSON      ┌──────▼───────┐  子进程/命令行  ┌───────▼────────┐
   │  前端 Web │ ◄──────────────► │  后端 FastAPI │ ◄───────────► │ 爬虫 .py 脚本   │
   │ Vite + TS│                  │   Python     │  (一次调用一个) │ 只 import      │
   └────┬─────┘                  └───┬──────┬───┘               │ crawler_kit+标准库│
        │                            │      │                   └───────┬────────┘
        │  播放(hls.js)              │      │                           │
        └────────────────────────────┘      │                           ▼
             ▲        流代理（**尚未做**）     │                      [ 源站 ]
             └──────────────────────────────┘
                                            │
                                     ┌──────▼──────┐
                                     │ MySQL（宝塔）│  激活码 / 设备（日后·远程配置）
                                     └─────────────┘

进程内还有两块**不属于任何一层**的东西，它们就住在后端进程里：

```
   ┌──────────────────────────┐   ┌────────────────────────────┐
   │ 内存缓存（TTL+LRU）        │   │ 每站守护                     │
   │ + SingleFlight 防击穿      │   │ 并发上限 · 熔断 · 半开探针    │
   └──────────────────────────┘   └────────────────────────────┘
```

**为什么没有"资产库"这一层了：** 最初的设想是把首页/详情回填进 MySQL 做冷通道。
实现时发现**内存缓存就够**：用户不到 30 人、单实例，缓存命中率和 Redis 完全一样，
却少了"一个必须活着的组件"和一套"库里的数据什么时候过期"的复杂度。
MySQL 因此只存**真正需要持久化的东西**（激活码、设备，以及日后的远程配置）。
需要"数据主动变新鲜"时用**定时预热**（主动把入口页抓进缓存），而不是建库回填。

### 四条不可动摇的原则

1. **契约先行（Contract-first）**
   `contracts/schemas/*.json` 是全局唯一事实源。前端 TS 类型由它生成，后端用它校验请求与响应，爬虫的输出必须过它的校验——**不合格直接拒收**，不许"凑合入库"。
   参考项目用 JSDoc 注释描述数据模型（`template.adapter.js` 里那一大段字段示范），注释是会腐烂的；Schema 不会。

2. **采集与在线服务物理隔离**
   爬虫**永远不跑在网关进程里**。参考项目用 `require()` 把 `sites/*.adapter.js` 载进主进程，任何一个适配器写出死循环或把内存吃满，整个网关跟着一起死。
   实现上比"独立进程池"更简单：**每次调用起一个子进程**，跑完就结束。
   网关只负责编排：给超时（到点直接 kill）、给并发上限、给熔断。
   没有常驻池就没有"池子里的进程发臭了要重启"这个问题 —— 代价是每次多花几十毫秒起进程，
   而这点开销相对源站动不动几秒的响应可以忽略。

3. **冷热双通道，不要把两种采集混在一起**
   - **热通道（实时）**：用户点了播放 → 网关当场向爬虫要 `play`。要求秒级，只用最轻量的请求，绝不在这条路上做"批量回填"。
   - **冷通道（离线）**：定时任务把首页/分类/详情元数据回填进资产库。慢、可以重试、可以失败。
   参考项目把所有采集都塞在用户请求路径上，用户流量直接等于源站流量，又慢又容易被封。

4. **播放地址绝不入库**
   数据库只存**可复现的定位符**：`site_id + vod_id + ep_index`。
   真正的 m3u8 每次播放现取现用。参考项目在文档里也写了这条（"绝不硬编码写入 m3u8 地址"）——这是它少数做对的地方，要保留。

## 三、端到端流程

所有内容接口都先过**会话守卫**（`X-Device-Token` → 必须是当前活跃设备），
否则 401 / 409。下面只画守卫之后的流程。

### 3.1 首页（`GET /api/v1/sites/{key}/home`）

```
前端 ──GET .../sites/ncat21/home──► 网关
                                     ├─ 1. 内容缓存命中 ──► 直接返回（0 毫秒）
                                     └─ 2. 未命中 ──► SingleFlight（同 key 只放一个）
                                                        └─► 子进程：ncat21.py home
                                                            （硬超时 20s，走每站/全站并发上限与熔断）
```
实现实测：`ncat21` 首页第一次 8.9 秒，第二次 **0.000 秒**。

**没有"降级为 degraded"这套了。** 最初担心的是"首页不能转圈"，而真正解决它的
不是降级，而是**主动预热**：每 N 小时把入口页预先抓进缓存，用户永远命中。
真到缓存也空了、源站也挂了的时候，就诚实报错（`UPSTREAM_TIMEOUT` 等），
而不是回一个"少了几个片子的首页" —— 后者更难排查。

### 3.2 详情（`GET /api/v1/sites/{key}/detail`）

```
前端 ──GET .../detail?vod_id=369061──► 网关
                                        ├─ 缓存（5 分钟）
                                        └─ 未命中 ──► 子进程：ncat21.py detail --id 369061
```
返回 `{ video, desc, episodes[], lines[] }`。其中每个 `episode` 都带 `play_id`，
前端要**原样回传**给播放接口（见 3.3）。

### 3.3 播放（最关键的一条链路）

```
前端 ──GET .../playback?vod_id=369061&ep=1&line=1&play_id=/play/369061-41-494.html──► 网关
        1. 子进程：ncat21.py play --id 369061 --ep 1 --line 1 --play-id /play/…
           （**不缓存地址**；带上 play_id 能省掉爬虫内部一次详情页抓取）
        2. 拿到 { url, format, headers }
        3. 判定 mode:
             direct → 直接回源站 url，headers（如 Referer）一起给前端
             proxy  → 签发 ticket，返回 /api/v1/stream/m3u8?ticket=<sig>
        4. hls.js 播放；m3u8 内部分片 URI 由网关重写为
           /api/v1/stream/seg?ticket=<sig>&u=<base64>
```

**实测省下来的时间：** 实测 7.249 秒 → **3.981 秒**（`play_id` 让爬虫不再为了
定位某一集而重抓详情页）。

**`play_id` 是一处信任边界。** 它由客户端回传、爬虫拿去直接抓取，
所以一个绝对 URL 就能让我们变成任意地址的代理（SSRF）。三层都拦：
后端只放行"像站内定位符"的值（不像就**丢掉并回退**，而不是报错——它是加速用的，
不该成为一个新的失败原因）、爬虫侧 `clean.safe_relative_path` 再拦一次、
拒绝协议相对写法（`//evil.com/x`，只检查"以 / 开头"正好会放它过去）。

**为什么必须签名 ticket**：如果代理接口是 `/stream?url=https://任意地址`，那这个后端就是一个公开的开放代理 + SSRF 跳板。参考项目里专门写了 `core/ssrf-guard.js`，说明这个问题真会出。新架构从一开始就用 HMAC 签名的 ticket 把 URL 绑死，客户端改不了目标。

## 四、爬虫层细节

语言与协议沿用 [crawler-plan.md](crawler-plan.md)（Python、`python <site>.py <cmd>`、stdout 只输出一行 JSON 信封、错误码统一）。在此基础上**新增四件事**：

### 4.1 能力清单（Capability Manifest）

`meta` 命令除了站点信息，还要声明自己支持哪些能力：

```json
{ "key": "demo", "name": "示例站", "version": "1.0.0",
  "base_url": "https://…", "mode": "proxy",
  "capabilities": ["home", "category", "search", "detail", "play"],
  "play_format": ["m3u8"] }
```

网关据此路由。某个站不支持 `search`，网关就明确返回"该源不支持搜索"，而不是把空列表伪装成"没搜到"。

### 4.2 稳定性机制（已实现的参数）

**没有常驻进程池** —— 每次调用起一个子进程（见原则 2）。所以也没有"自动重启"。

| 机制 | 实现值 | 演变说明 |
| --- | --- | --- |
| 进程隔离 | 一次调用一个子进程 | 比常驻池更简单，且没有"进程发臭"问题 |
| 硬超时 | 元数据 **20s** / 播放 **25s** | 初稿写的 3s/5s **完全不够**：实测 ncat21 首页 5.2~8.9s、播放 4.0~7.2s。5s 那种值就是"平时刚好、网络一抖就 504" |
| 并发上限 | 每站 **2**，全局 **4** | 初稿的"每站 4/全局 32"对一个 10Mbps 的 VPS 太激进了 |
| 熔断 | 连续失败 **5** 次 → 冷却 **60s** → 半开放**一个**探针 | 初稿方向对，但漏了两条关键的：`NOT_FOUND`/`UNSUPPORTED` **不算故障**；`meta` 的成功**不参与计数** |
| 抢不到槽位 | 排队 20s 后回 `UPSTREAM_BUSY` | 快速失败优于无限等待（等待会连着占住连接与线程） |

两条脱胎于实战的细则（详见 [steps/04](steps/04-cache-and-resilience.md)）：

* **`meta` 不能参与熔断计数。** `run` 每次都先跑 `meta`，如果它的成功也清零失败计数，
  序列就变成"内容失败 → meta 成功 → 计数清零"，于是"meta 能通、抓内容就超时"的源
  **永远熔断不掉** —— 而那正是最该熔断的一类。
* **单请求缓存不能代替主动预热。** TTL 是被动过期：到点后由**下一个来访者**
  触发重抓、由他承担十几秒等待，而且没人来的话数据会一直旧着。

### 4.3 快照回归（离线测试）

`--offline` 模式：爬虫不联网，从 `tests/fixtures/<site>/*.html` 读本地快照。
这样"源站改版"会变成 **CI 里的红灯**，而不是线上用户的空白页。CI 每次改动跑全量快照回归。

### 4.4 结构指纹自检（Selftest）

每个爬虫提供 `selftest` 命令，返回一组"关键选择器命中计数"：

```json
{ "selectors": { ".vodlist .item": 24, "#episode-list li": 12, "script[src*=player]": 1 } }
```

网关定时（如每 30 分钟）跑一次，与基线比对。命中数骤降（比如 24 → 0）说明站改版了，**自动熔断该源并告警**——用户看到的是"该源维护中"，而不是"解析失败"。

### 4.5 硬约束

爬虫只允许 `import crawler_kit` + Python 标准库；不读写文件（快照模式除外）；不直接开 socket；不 `eval`。理由：线上不为每个爬虫准备依赖、白名单校验有边界、本地与线上能力一致。

## 五、后端层细节

### 5.1 技术选型（建议）

| 选择 | **实际采用** | 为什么改成这个 |
| --- | --- | --- |
| 运行时 | **Python 3.11+** | 爬虫已经是 Python，后端也用 Python 就能**共用同一套校验模型**；两套语言意味着校验逻辑要写两遍 |
| Web 框架 | **FastAPI** | 用 Pydantic 模型直接生成 OpenAPI，等于"接口定义即文档"（`/docs` 不会和实现脱节）；`Depends` 让"守护卫挂在 router 上"成为自然写法 |
| 数据校验 | **Pydantic v2** | 同一个模型干三件事：入参校验、出参序列化、导出 JSON Schema（给前端与爬虫用） |
| 数据库 | **MySQL 5.7/8**（宝塔） | 沿用现有环境。**表结构只用可移植类型**，本地/测试跑临时 SQLite |
| ORM | **SQLAlchemy 2.0 + PyMySQL** | 同步就够（量级小），不必上 async 驱动 |
| 缓存 | **进程内 TTL+LRU + SingleFlight** | **不上 Redis**：单实例、用户不到 30 人，命中率和 Redis 一样，却少一个必须活着的组件 |
| 后台任务 | **一个后台线程**（`core/scheduler.py`） | 现在只有一个周期性任务（预热），APScheduler/Celery 带来的配置与故障模式比它自己还大 |
| 队列 | **不需要** | 没有"必须重试到成功"的离线任务；预热是可失败的周期行为 |

> 唯一的硬性反对项：**不要再把爬虫 import 进主进程**。

### 5.2 模块划分

```
backend/app/
  api/         薄路由（只声明参数与转发）+ deps.py（拿依赖 · 两套守卫）
  services/    业务编排：catalog · site · activation · warmup（不 import fastapi）
  crawler/     子进程调度：runner · registry · guard · validate
  cache/       ttl · singleflight · content（通用原语，不含业务知识）
  models/      ORM（数据库形状）
  schemas/     Pydantic（接口形状）= 契约唯一来源
  db/          引擎 / 会话 / 建表
  core/        config · clock · logging · errors · middleware · handlers · scheduler
  contracts.py 把模型导出成 contracts/schemas/*.json
  main.py      只组装：建 app、挂中间件、注册异常处理、挂路由、起后台任务
```

依赖方向是**单向**的：`api → services → crawler / cache / db → models`。
`services/` **不 import fastapi**，所以能脱离 HTTP 直接单测。

未来的 `stream/`（m3u8 重写 + ticket）与 `admin/` 里的业务逻辑分别属于
PROGRESS.md 里的阶段 8 与阶段 7，现在后台只有"看状态 + 刷缓存"两个接口。

### 5.3 统一响应信封

```json
{ "ok": true,  "data": { }, "error": null, "request_id": "…" }
{ "ok": false, "data": null, "error": { "code": "UPSTREAM_TIMEOUT", "message": "…" }, "request_id": "…" }
```

与爬虫层信封**同构**（多一个 `request_id`，命名从 `requestId` 改成 `request_id`
以对齐 Python 侧的字段风格）。前端只需写一套错误处理；排查问题时 `request_id`
能从网关日志一路串到爬虫的 stderr。

**连框架自己抛的 404 也走信封**（在 `core/handlers.py` 里统一接管）——
否则前端会遇到"有的错是 JSON、有的错是 HTML"。

### 5.4 数据库（只存真正需要持久化的东西）

| 表 | 存什么 | 状态 |
| --- | --- | --- |
| `activation_codes` | 激活码、时长（小时）、首次激活时间、到期时间、停用时间、当前活跃设备 | ✅ 已实现 |
| `devices` | 设备令牌、展示名、最后心跳时间 | ✅ 已实现 |
| `remote_config` | 源开关、公告弹窗、kill switch | ⬜ 阶段 5 |
| `audit_log` | 管理操作留痕 | ⬜ 阶段 7 |

**首页/详情/剧集都不入库。** 它们是缓存里的东西（可以随时重新抓），
入库只会带来"库里的数据什么时候过期"这一整类新问题。

> `vod_id` 用**完整路径**而不是从 URL 正则抠出来的数字 —— 分页、多线路时数字极易撞车。
> 这一条在 ncat21 上已经被验证（它的多线路集号会重复，只有路径唯一）。

### 5.5 安全清单（参考项目踩过的坑）

- 流代理走 **ticket 签名**，不接受裸 `?url=`（防 SSRF / 开放代理）
- 图片代理同理，且限制目标域名白名单
- 出站请求统一走 `http-client`，强制超时 + 响应体大小上限
- **接入新源时必须实测「清单 + 分片 + 密钥」三者的 CORS**，不能只看清单。
  只测清单是最容易骗过自己的测法：清单开放、分片在另一个 CDN 域名上不带 CORS 时，
  浏览器会先拿到清单再在分片处全量失败，现象是"播放器一直转圈"。
  （2048ai.vip 实测三者全开，所以它能 `mode: direct`。）
- 管理接口 `ADMIN_TOKEN` + 审计日志；紧急熔断开关（kill switch）
- 配额与限流按设备/账号维度，**不要只信 `X-Device-Id`**（它是客户端自填的，可伪造）

## 六、前端层细节

### 6.1 技术选型

| 选择 | 建议 | 相对参考项目的改动 |
| --- | --- | --- |
| 构建 | Vite（沿用） | — |
| 语言 | **TypeScript** | 参考是 vanilla JS，字段漂移只能上线才发现 |
| 类型来源 | 由 `contracts/schemas` 生成 | 后端改契约 → 前端编译期报错 |
| 框架 | **Vue3**（已定） | 组件化，避免手写 DOM |
| 播放 | hls.js（沿用） | 加错误重试与降级 |
| 样式 | 原生 CSS 变量 + 设计令牌 | 不引 UI 库，保持轻 |

### 6.2 页面与组件

```
src/
  api/         按契约生成的类型 + 一个 fetch 封装（统一拆信封、统一错误提示）
  components/
    VideoCard        全站唯一卡片（只吃 VodItem，不认任何源站字段）
    SiteSwitcher     源站切换（含"维护中"状态）
    Player           hls.js 封装：direct / proxy 透明切换，失败自动重试一次
    EpisodeList      剧集列表
  pages/  Home · Catalog · Detail · Search · Mine
  stores/ 轻量状态（源站、播放进度、鉴权）
```

### 6.3 前端的硬规矩

- 前端**只依赖契约字段**。源站的私有字段一律在后端归一化，不许泄漏到 UI。
- 播放地址是**一次性**的：过期（403/404）要能自动重新请求 playback 接口拿新地址，而不是提示"播放失败"。
- 空态要分三种：**真的没有** / **源不支持** / **源维护中**。参考项目把三者混成"空列表"，用户在体验上完全分不清。
  后端已经把前两种分开了：该源不支持 `search` 时返回 `UNSUPPORTED`（501），
  而不是空列表。
- **激活成功后要自己保存 `device_token`**，并在收到 `409 SESSION_KICKED` 时
  停止播放、提示"已在其他设备登录"、等用户**手动**点"在此设备继续"。
  发现自己被踢就自动抢回来的话，两台设备会无限互踢。

## 八、里程碑（顺序很重要）

| 阶段 | 交付 | 验收 | 状态 |
| --- | --- | --- | --- |
| **M0 契约 + 骨架** | `contracts/` 定稿；目录建好 | 不联网就能跑全部测试 | ✅ 已完成 |
| **M1 爬虫 1 个站** | 6 个命令全通（见 crawler-plan） | 命令行能拿到真数据 | ✅ 已完成（ai2048 + ncat21）|
| **M2 后端网关** | 子进程调度 + 缓存 + 稳定性 | 首页→详情→播放端到端真能跑 | ✅ 已完成（流代理除外）|
| **M2.5 门（鉴权）** | 激活码 + 单会话互踢 | 没码进不来、两台互踢 | ✅ 已完成 |
| **M3 远程配置 + 部署** | 源开关 · 公告 · kill switch；uvicorn+nginx+systemd | 一键关掉某个源 | ⬜ 下一步 |
| **M4 前端** | 首页/分类/详情/播放器 | 手机浏览器上完整看一集 | ⬜ |
| **M5 后台面板** | 爬虫上传 · 源开关 · 踢设备 · 封码 | 不用改代码就能运维 | ⬜ |
| **M6 流代理（按需）** | m3u8 重写 + 分片转发 + ticket 签名 | 只有某个源真需要时才做 | ⬜ |
| **M7 采集工场** | 可视化生成器：声明式配置 + 逃生舱 | 第 3 个源接入时间明显缩短 | ⬜ |
| **M8 ipa** | Capacitor 包壳 + WebView 直载远程 | 打包一次，之后部署即热更 | ⬜ 最后一步 |

> **顺序上的最大纠正：** 参考项目把"采集工场 + 代码加密（Plove Armor）"
> 做得极重，而基础契约和隔离反而最薄。加密适配器只是"不让别人看懂"——
> 真正的护城河是**快**、**稳**、和**接入新源的效率**。工场应该是 M7，不是 M0。
>
> **第二个纠正（写实现时才看清）：** 原计划里"冷通道回填进资产库"这一步
> 被**缓存 + 定时预热**代替了。少一层存储，少一整类"过期"问题。

## 九、与参考项目的逐条对照

| 维度 | 参考项目 | 本方案 | 为什么更好 |
| --- | --- | --- | --- |
| 爬虫运行位置 | `require()` 进网关进程 | 一次调用一个子进程 | 单个源崩溃不再拖垮全站 |
| 数据契约 | JSDoc 注释 | Pydantic 模型 → JSON Schema | 契约可校验、可生成类型、不会腐烂 |
| 采集时机 | 全在用户请求路径上 | 请求时按需抓 + **定时预热入口页** | 入口永远命中缓存；源站压力可控 |
| 缓存 | 进程内 TTL | TTL+LRU + singleflight 防击穿 | 同时到达的那批也只抓一次 |
| 播放安全 | 签名 ticket（有 ssrf-guard） | 同思路，从第一天就内建 | 防开放代理/SSRF |
| 源站改版 | 线上才发现 | 快照回归 + 结构指纹熔断 | 改版变成 CI 红灯 |
| 适配器加密 | AES-256-CTR 混淆 | **不做加密** | 没有秘密可藏；靠隔离+权限，而不是靠看不懂 |
| 爬虫实现 | 大量正则启发式散落在各适配器 | 启发式收敛进 crawler_kit，站点文件尽量短 | 第 2、3 个源才可能真的"快" |
| 测试 | 2 个集成测试文件 | 每源一份快照回归 | 改版有安全网 |
| 前端 | vanilla JS，无类型 | TS + 生成类型 | 契约漂移在编译期暴露 |
| 空态 | 一律空列表 | 区分"没有/不支持/维护中" | 可诊断的用户体验 |
